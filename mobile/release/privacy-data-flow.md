# Privacy declaration worksheet

Prepared 5 September 2026. This is an engineering evidence draft, not a completed App Store Connect or Play Console declaration. Provider/account configuration and the final signed build still need verification. It would be inaccurate to describe this app as collecting no data. Code paths in the evidence column are relative to the mobile package root; `../netlify` refers to the repository's website functions.

## Observed data flows

Weather (`/api/weather`) and AI reply reports (`/api/planner-report`) use `https://destination-paradise-mobile.netlify.app`, alongside the public privacy page at `https://destination-paradise-mobile.netlify.app/mobile-privacy.html`. Production deployment `6a9c808c5bf2edc8e8dfa90a` was verified: weather and privacy returned 200, report GET/invalid POST returned 405/400 without email. Successful report receipt remains unverified. Planner chat (`/api/planner`) and quotes (`/api/planner-send`) continue to use `https://yournexttriptoparadise.com`. Main-website photos and travel/support links also use that original domain. Detailed release evidence is in `README.md` and `../VALIDATION.md`.

## Apple draft mapping

| Data category | Proposed treatment and reason |
| --- | --- |
| Contact Info: Name, Email Address, Phone Number | Collected for optional quote functionality and potentially asked for in AI chat. Linked to the user in email/transcript. App Functionality; no ad-tracking purpose found. Phone is optional. |
| User Content: Other User Content | AI chat and travel preferences/draft. Conservative linked-to-user treatment where sent with contact details. App Functionality; assess Product Personalization for tailored suggestions. |
| User Content: Customer Support | New AI-content reports contain selected output, reason and optional notes. Declare the appropriate user-content/support category and App Functionality purpose. No account/contact identity is automatically attached, but text itself may identify someone; do not promise anonymity. |
| Diagnostics: Other Diagnostic Data / Performance Data | Conditional on actual retained server monitoring/traces and final native SDK behavior. Verify production Sentry and hosting logs before selecting categories/linkage. |
| Other Data Types / identifiers inferred from IP | Review retained IP/access metadata against Apple's taxonomy and provider use. No advertising/device identifier API was found; do not equate this with no network metadata. |
| Precise or Coarse Location | No user-location feature found. Fixed Zanzibar coordinates and public destination pins are not the user's physical position. If providers derive and retain user location from IP, assess that separate behavior. |
| Search History | Explore searches are local source filtering; no search-text transmission found. |
| Tracking | No cross-company advertising tracking purpose found. Confirm provider contracts/use before attesting. |

Apple excludes strictly on-device processing from collection and treats retention beyond servicing the request differently from instantaneous processing. Generic free text maps to user content; specifically requested contact fields need their contact categories. Apply the final provider practices, not just the absence of a mobile database. [Apple privacy definitions](https://developer.apple.com/app-store/app-privacy-details/)

## Facts the owner must resolve

1. Actual legal operator/contact and the applicable retention/deletion process for enquiries, team mailbox, Resend, provider logs, AI prompts, and later AI reports. Do not invent retention periods.
2. Anthropic account terms: processing regions, retention, any zero-retention arrangement, training/data-use terms and subprocessor obligations. Source alone proves neither zero retention nor a no-training promise.
3. Resend and team mailbox retention/access, optional Sentry enablement/traces, and Netlify logging behavior. `sendDefaultPii:false` does not prove no request-derived diagnostics.
4. Hosting access-log retention still needs provider/account confirmation; code caching applies to public weather readings, not log retention. WeatherKit activation and the dedicated proxy's live deployment are verified under the existing membership allowance. Service keys stay on the server, and no Open-Meteo purchase or new weather subscription was made. Final signed-build runtime checks remain separate from the public endpoint check.
5. Final binary privacy manifests/permissions and any release-only SDKs. Do not infer production permissions from Expo Go.
6. Any business follow-up beyond the requested quote. No newsletter opt-in or advertising transmission was found in the native flow; marketing reuse would change the declarations.
